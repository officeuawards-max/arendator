# Arendator Awards — лендинг бронирования билетов

Новая версия страницы `aawards.ru/tickets`. Статичные HTML + CSS + JS, **без сборки и без зависимостей**.

**Дизайн — по макету дизайнера:** чёрный + золото, светлые кремовые секции, заголовки антиквой (Playfair Display), текст — Roboto.

**Покупки на сайте нет.** Все кнопки ведут к форме бронирования (блок «Оформление билета» внизу страницы). Заявка уходит на наш сервер, сервер создаёт **лид в Битрикс24**, дальше с ним работают менеджеры по продажам.

```
index.html                          ← вся разметка (блоки 01–11 подписаны комментариями)
assets/css/style.css                ← стили (все классы с префиксом aa-, конфликтов с Bootstrap нет)
assets/js/config.js                 ← НАСТРОЙКИ: адрес для заявок, цены, дата таймера, остаток мест, Метрика
assets/js/seating.js                ← СХЕМА ЗАЛА: столы, цвета зон, вместимость, координаты
assets/js/consent.js                ← cookie-баннер, согласие на аналитику, реквизиты оператора в документах
assets/js/main.js                   ← логика: форма бронирования, схема, таймер, анимации
assets/fonts/                       ← шрифты локально: Roboto (от заказчика, исходник — fonts/source/Roboto.rar) и Playfair Display (OFL)
legal/                              ← Политика ПД, Согласие на обработку ПД, Согласие на рассылки, Политика cookie
assets/img/                         ← фото и логотипы (список имён — в assets/img/README.md)
backend/laravel/TicketLeadController.php  ← приём заявки → лид в Битрикс24 (Laravel)
backend/bitrix-lead.php             ← то же самое одним PHP-файлом, без фреймворка
legacy/                             ← исходники старой страницы и картинка схемы — для сверки
```

## Как посмотреть

```bash
python3 -m http.server 8000   # из корня репозитория → http://localhost:8000
```
Пока `endpoints.lead` в `config.js` пустой, страница работает в демо-режиме: форма показывает «Спасибо», но ничего не отправляет (данные пишутся в консоль браузера).

## Бронирование → Битрикс24

### Кнопки
Любой элемент с `data-book` открывает одну и ту же форму с уже выбранным форматом:

```html
<button data-book="vip">Забронировать</button>        <!-- vip | business | personal | table -->
<button data-book="question">Задать вопрос</button>   <!-- форма без выбора формата -->
```

В форме: формат (4 варианта), количество гостей с ориентировочной суммой, ФИО, телефон (с маской), email, компания, должность, комментарий, согласие на обработку ПД и скрытое антиспам-поле.

### Что уходит на сервер
`POST {endpoints.lead}`, FormData, заголовки `X-CSRF-TOKEN` и `X-Requested-With`:

| Поле | Значение |
|------|----------|
| `intent` | `booking` или `question` |
| `package` | `vip` / `business` / `personal` / `table` (нет у вопроса) |
| `guests` | количество гостей, 1–50 (нет у вопроса) |
| `name`, `phone`, `email`, `company`, `position`, `comment` | данные из формы |
| `consent_pd` | `1` — согласие на обработку ПД (обязательно, без него сервер вернёт 422) |
| `consent_ads` | `1` / `0` — согласие на рассылки (необязательно) |
| `consent_version`, `consent_at` | версия документов и время согласия в браузере |
| `utm_source` … `utm_term` | UTM-метки, запоминаются на время визита |
| `page`, `referrer` | страница заявки и откуда пришёл посетитель |
| `ym_client_id` | ClientID Метрики, если счётчик есть на странице |
| `website` | антиспам: у человека всегда пустое |

Ответ 2xx означает успех: гость видит «Спасибо! Заявка отправлена». Любой другой ответ показывает ошибку, и заявку можно отправить повторно.

### Что создаётся в Битрикс24
Метод `crm.lead.add`:
- **TITLE**: «Arendator Awards 2026 — Бизнес, гостей: 3» или «… — вопрос с сайта»
- **NAME, COMPANY_TITLE, POST, PHONE, EMAIL** — из формы
- **OPPORTUNITY**: цена × гости, `CURRENCY_ID=RUB`. Цены считаются **на сервере**, значениям из браузера не доверяем. У стола и вопроса суммы нет.
- **COMMENTS**: формат, гости, сумма, комментарий, страница, источник перехода, ClientID Метрики
- **UTM_SOURCE … UTM_TERM**, `SOURCE_ID=WEB`, `SOURCE_DESCRIPTION` = «Лендинг билетов aawards.ru/tickets»
- **ASSIGNED_BY_ID**: ответственный, если задан в настройках

Проверено на имитации Битрикс24: заявка с формы доходит до `crm.lead.add` со всеми полями выше. На реальном портале не проверялось.

### Подключение (Laravel, рекомендуется)
1. В Битрикс24 создать входящий вебхук: *Разработчикам → Другое → Входящий вебхук*, права — **только CRM**.
2. Скопировать `backend/laravel/TicketLeadController.php` в `app/Http/Controllers/`.
3. Добавить роут:
   ```php
   Route::post('/tickets/lead', [\App\Http\Controllers\TicketLeadController::class, 'store'])
       ->middleware('throttle:10,1')->name('tickets.lead');
   ```
4. В `.env`:
   ```
   BITRIX24_WEBHOOK=https://ваш-портал.bitrix24.ru/rest/1/xxxxxxxxxxxxxxxx/
   BITRIX24_ASSIGNED_ID=            # необязательно
   ```
   В `config/services.php` добавить блок `bitrix24` (текст — в шапке контроллера).
5. В `assets/js/config.js` указать `endpoints.lead: '/tickets/lead'`.

**Без Laravel:** положить `backend/bitrix-lead.php` на сервер, задать переменную окружения `BITRIX24_WEBHOOK` и указать путь к файлу в `endpoints.lead`.

> ⚠️ Адрес вебхука — секрет. Он даёт доступ к CRM, поэтому **никогда** не вызывайте Битрикс напрямую из браузера и не кладите вебхук в `config.js` или в репозиторий. Только через сервер, как в файлах из `backend/`.

Если лид не создался, причина пишется в лог (`storage/logs` в Laravel или `error_log` PHP), вместе с данными заявки, чтобы её не потерять.

### Прямые ссылки для рекламы и рассылок
`…/tickets#book-vip`, `#book-business`, `#book-personal`, `#book-table`, `#book-question` сразу прокручивают к форме с нужным форматом (или в режим «задать вопрос»).

### Цены и «Осталось мест»
Все цены на странице (карточки, таблица, схема, форма, нижняя панель) подставляются из `config.js → tickets`. Блок «Осталось мест» показывает цифры из `config.js → seatsLeft` (`vip`, `business`); пока там `null`, вместо цифр выводится нейтральная фраза.

### Метрика
Счётчик `47656444` подключает layout сайта. Лендинг отправляет цели `tickets_book_open` (нажата кнопка бронирования) и `tickets_book_sent` (заявка отправлена); их нужно завести в Метрике. Имена меняются в `config.js → analytics.goals`.

## Схема зала
План перенесён 1:1 с утверждённой картинки (`legacy/seating-plan.jpg`): стены, welcome-зона, бар, сцена, вход, колонна, 72 стола, подписи «до N чел». Оформление — в стиле макета (тёмный фон, золото, круглые столы с кольцом стульев), легенда — справа от схемы.

**Выбирается зона (категория), а не стол.** Клик по любому столу или по пункту легенды подсвечивает **все столы этого цвета** и приглушает остальные. Справа (на телефоне — внизу) показывается общая информация о зоне:
- формат и цена за гостя;
- какие столы в зоне («на 2 и 4 гостя»);
- что входит;
- кнопка «Забронировать», которая ведёт к форме с этим форматом.

Номер стола нигде не показывается и в заявку не передаётся. При наведении подсвечивается вся зона, а подсказка говорит о формате, а не о столе.

**Фиолетовые столы — «Места закончились».** Это столы с `booked: true` в `seating.js`. По клику подсвечивается вся фиолетовая зона и показывается карточка «Аншлаг» с неактивной кнопкой «Бронирование недоступно».

**Где что менять:**
- `assets/js/seating.js` — столы (номер, зона, вместимость, координаты, `booked`), а также цвета и описания зон.
- `index.html`, блок 05 — статичная часть плана (стены, бар, сцена) и легенда.
- Необязательно: `config.js → seating.statusUrl` — адрес, отдающий `{"booked": ["702", …]}`, чтобы фиолетовые столы обновлялись без правки файла.

Цвета — в золотой гамме макета: **VIP — золото `#D4AE6A`, Business — шампань `#EEDDB9`, Персональная — бронза `#A89378`**, «Места закончились» — фиолетовый `#8E7BC2`. (На утверждённой картинке было: ВИП — зелёный, Бизнес — красный, Персональные — жёлтый; зоны те же.)

## Персональные данные (152-ФЗ, редакция 2025–2026)

Что учтено на сайте и почему:

| Требование | Где закон | Что сделано |
|---|---|---|
| Согласие на обработку ПД — **отдельно** от других документов (с 01.09.2025) | ч. 1 ст. 9 152-ФЗ в ред. 156-ФЗ | Отдельная страница `legal/consent.html` и отдельная галочка в форме |
| Согласие активное, конкретное, однозначное | ч. 1 ст. 9 | Галочки **не проставлены** заранее; без галочки о ПД заявка не отправляется, и форма объясняет почему |
| Рассылки — только с отдельного согласия | ст. 18 38-ФЗ «О рекламе» | Отдельная **необязательная** галочка и страница `legal/consent-ads.html`; признак уходит в лид |
| Политика обработки ПД опубликована на сайте | ч. 2 ст. 18.1 | `legal/privacy.html`, ссылки в форме и в подвале |
| Оператор должен уметь доказать согласие | ч. 3 ст. 9 | Сервер пишет журнал: время, IP, браузер, версия документов, контакты. Та же информация попадает в лид Битрикса |
| Первичный сбор ПД — только в базы данных в РФ (с 01.07.2025) | ч. 5 ст. 18 в ред. 23-ФЗ | Форма шлёт данные на наш сервер, затем в Битрикс24. Сервер и портал Битрикс24 должны быть в РФ (см. чек-лист) |
| Cookie и Яндекс Метрика — ПД, нужен выбор пользователя | позиция РКН, 152-ФЗ | Баннер «Принять все / Только необходимые», `legal/cookies.html`, кнопка «Настройки cookie» в подвале. Цели Метрики, ClientID и сохранение UTM — только после «Принять все» |
| Не передавать IP посетителей за рубеж без необходимости | 152-ФЗ, локализация | Шрифты Roboto и Playfair Display хранятся локально (`assets/fonts`), запросов к Google Fonts нет |
| Повышенные штрафы с 30.05.2025 | 420-ФЗ, КоАП ст. 13.11 | — (стимул сделать всё выше) |

### Документы (`legal/`)
- `privacy.html` — Политика обработки персональных данных: цели, данные, основания, сроки, обработчики, локализация, права, меры защиты.
- `consent.html` — Согласие на обработку ПД, отдельный документ.
- `consent-ads.html` — Согласие на рассылки, необязательное.
- `cookies.html` — Политика cookie с таблицей cookie.

Реквизиты оператора подставляются из `config.js → operator`; уже известные (из карточки ООО «УРБАН И ТОЧКА») вписаны в HTML документов напрямую, чтобы их было видно и без JavaScript. Их нужно заполнить один раз, и они появятся во всех документах и в подвале. Пока поле пустое, на странице видна жёлтая заглушка `[…]`, и пропустить её трудно. Версия и дата документов (`docsVersion`, `docsDate`) уходят вместе с каждой заявкой. При новой редакции поменяйте версию, и баннер cookie покажется всем заново.

> ⚠️ Тексты документов — шаблон, составленный по требованиям закона. **Перед публикацией их должен проверить юрист компании** и сверить с реальными процессами: кто обрабатывает данные, сроки хранения, кто ответственный.

### Cookie и Метрика
- Баннер с юмором про коммерческую недвижимость: 6 шуток в случайном порядке («Файлы cookie ищут арендатора», «Cookie — лучший cap rate на рынке», «Cookie: сделка без брокера»…) и печенька-бизнес-центр, которую откусывают при согласии. Тексты — массив `JOKES` в `consent.js`.
- Слово cookie есть везде, где пользователь принимает решение: метка «Сайт использует файлы cookie», каждый заголовок, кнопки **«Принять все cookie»** и **«Только необходимые cookie»**. Шутка — только мелкой подписью под кнопкой («и подписать договор аренды»).
- Под каждой шуткой стоит строка **«По делу»** простыми словами, а кнопка отказа «Только необходимые» так же заметна, как кнопка согласия. Это важно: шутка не должна скрывать смысл согласия.
- `consent.js` показывает баннер и хранит выбор (`localStorage: aa_cookie_consent`, привязан к версии документов).
- Выбор доступен в JS: `window.aaConsent = { analytics: true|false }`. При изменении срабатывает событие `aa:consent`.
- Если счётчик Метрики подключает **layout сайта**, его нужно запускать только после согласия:
  ```js
  function startMetrika() { /* стандартный код счётчика 47656444 */ }
  if (window.aaConsent && window.aaConsent.analytics) startMetrika();
  document.addEventListener('aa:consent', function (e) { if (e.detail && e.detail.analytics) startMetrika(); });
  ```
  Для отдельной страницы можно выставить `config.js → analytics.loadMetrika: true`, и лендинг сам подключит счётчик после согласия.

### Сервер
- Обработчики из `backend/` принимают заявку только с `consent_pd=1` (иначе 422) и пишут журнал согласий: Laravel — `storage/logs/pd-consents-*.log`, PHP-файл — путь из `PD_CONSENT_LOG`. Журнал храните на сервере в РФ весь срок обработки данных.
- В лид Битрикса добавляются строки «Согласие на обработку ПД: да, ред. …, время, IP» и «Согласие на рассылки: да/нет».

## Перенос в Laravel (Blade)

Лендинг больше не зависит от формы оплаты сайта. jQuery, iCheck и прочее не нужны, так что подойдёт любой вариант.

**Вариант А: внутри layout сайта**
1. Скопировать `assets/` в `public/landing/tickets/`.
2. `resources/views/tickets/landing.blade.php`:
   ```blade
   @extends('layouts.new.usercp')
   @section('styles')
       <link rel="stylesheet" href="{{ asset('landing/tickets/css/style.css') }}?v=1">
       {{-- + инлайн-скрипт из <head> index.html (подмена картинок и флаг анимаций) --}}
   @endsection
   @section('content')
       {{-- всё от <div class="aa"> до </div><!-- /.aa --> из index.html --}}
   @endsection
   @section('scripts')
       <script src="{{ asset('landing/tickets/js/config.js') }}?v=1"></script>
       <script src="{{ asset('landing/tickets/js/consent.js') }}?v=1"></script>
       <script src="{{ asset('landing/tickets/js/seating.js') }}?v=1"></script>
       <script src="{{ asset('landing/tickets/js/main.js') }}?v=1" defer></script>
   @endsection
   ```
3. Пути `assets/…` заменить на `/landing/tickets/…`. Страницы `legal/*.html` выложить рядом (например `/tickets/legal/…`) и поправить в них пути к `../assets/`, либо сделать из них Blade-страницы с тем же содержимым.
4. В `<head>` должен быть `<meta name="csrf-token" content="{{ csrf_token() }}">`.
5. Если у layout своя шапка, блок `<header class="aa-nav">` можно удалить.

Все классы начинаются с `aa-`, сбросы стилей действуют только внутри `.aa`. Стили сайта и Bootstrap лендинг не ломают, и сам лендинг на сайт не влияет.

**Вариант Б: отдельная страница.** `index.html` как есть, с CSRF-мета, если заявки принимает Laravel.
